Opacity of Classical Systems

Two runs differ on whether a secret event occurred, yet produce the same observable event sequence a·b·c. No clocks, no probabilities, one fixed observer: the system is opaque with respect to this secret if a cover run like this always exists.
● Scope of this page

This page covers the setting where the field started: discrete event systems modeled as finite automata, labeled transition systems, or Petri nets, with no notion of real time, no randomness, and a single observer watching a fixed set of observable events.

This is the setting the foundational definitions were built for, and it's where the largest share of the opacity literature still sits: the core notions (language-based, current-state, initial-state, K-step, infinite-step opacity), the algorithms that verify them, and the mechanisms (supervisory control, insertion and edit functions, dynamic masks) that enforce opacity on a system that doesn't already have it.

Notions & Verification

The core literature on opacity for finite-state systems: articles that introduce a notion of opacity, study its decidability or complexity, or develop an algorithm to verify it. Most use plain finite automata as the underlying model and are grouped by what they contribute; a separate group uses Petri nets, which raise their own decidability questions distinct from automata.

Core notions & definitions

Articles that define opacity or a closely related notion: state-based and language-based definitions on automata and labeled transition systems, a notion of secrecy together with a weaker version, and opacity for cryptographic protocols.

  • Notions of Security and Opacity in Discrete Event Systems
    Anooshiravan Saboori, Christoforos N. Hadjicostis · 46th IEEE Conference on Decision and Control (CDC 2007), pp. 5056–5061 · IEEE Xplore
    Source of current-state opacity, here with a K-step strengthening.
    classical · finite-automata · opacity
    Show abstractHide abstract
    In this paper, we follow a state-based approach to extend the notion of opacity in computer security to discrete event systems. A system is (S, P)-opaque if the evolution of its true state through a set of secret states S remains opaque to an observer who is observing activity in the system through the projection map P. In other words, based on observations through the mapping P, the observer is never certain that the current state of the system is within the set of secret states S. We also introduce the stronger notion of (S,P, K)-opacity which requires opacity to remain true for K observations following the departure of the system's state from the set S. We show that the state-based definition of opacity enables the use of observer constructions for verification purposes. In particular, the verification of (S,P, K)-opacity is accomplished via an observer with K-delay which is constructed to capture state estimates with K-delay. These are the estimates of the state of the system K observations ago and are consistent with all observations (including the last K observations). We also analyze the properties and complexity of the observer with K-delay.

  • Opacity of Discrete Event Systems and Its Applications
    Feng Lin · Automatica, 47(3), pp. 496–503, 2011 · doi.org/10.1016/j.automatica.2011.01.002
    classical · finite-automata · opacity
    Show abstractHide abstract
    In this paper, we investigate opacity of discrete event systems. We define two types of opacities: strong opacity and weak opacity. Given a general observation mapping, a language is strongly opaque if all strings in the language are confused with some strings in another language and it is weakly opaque if some strings in the language are confused with some strings in another language. We show that security and privacy of computer systems and communication protocols can be investigated in terms of opacity. In particular, two important properties in security and privacy, namely anonymity and secrecy, can be studied as special cases of opacity. Also in this paper we provide algorithms for checking strong opacity and weak opacity for systems described by regular languages and having a generalized projection as the observation mapping.

Verification & complexity

  • Verification of K-Step Opacity and Analysis of Its Complexity
    Anooshiravan Saboori, Christoforos N. Hadjicostis · IEEE Transactions on Automation Science and Engineering, 8(3), pp. 549–559, 2011 · doi.org/10.1109/TASE.2011.2106775
    classical · finite-automata · opacity
    Show abstractHide abstract
    Motivated by security and privacy considerations in a variety of applications of discrete event systems, we describe and analyze the computational complexity required for verifying the notion of K-step opacity for systems that are modeled as nondeterministic finite automata with partial observation on their transitions. Specifically, a system is K-step opaque if, at any specific point within the last K observations, the entrance of the system state to a given set of secret states remains opaque (uncertain) to an intruder who has complete knowledge of the system model and observes system activity through some natural projection map.   • Verification of Infinite-Step Opacity and Complexity Considerations
    Anooshiravan Saboori, Christoforos N. Hadjicostis · IEEE Transactions on Automatic Control, 57(5), pp. 1265–1269, 2012 · doi.org/10.1109/TAC.2011.2173774
    classical · finite-automata · opacity
    Show abstractHide abstract
    We describe and analyze the complexity of verifying the notion of infinite-step opacity in systems that are modeled as non-deterministic finite automata with partial observation on their transitions. Specifically, a system is infinite-step opaque if the entrance of the system state, at any particular instant, to a set of secret states remains opaque (uncertain), for the length of the system operation, to an intruder who observes system activity through some projection map. Control & Enforcement

Making a system opaque, or enforcing opacity when it is initially absent, by restricting or modifying its behavior. Four mechanisms appear across this literature: supervisory control (disabling events), insertion and edit functions (adding or changing events in the observation channel), obfuscation policies (altering what the observer sees at the output), and approaches that account for an active or adversarial intruder.
